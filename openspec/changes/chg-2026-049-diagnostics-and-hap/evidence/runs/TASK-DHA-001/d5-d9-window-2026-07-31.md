## D5:`bm install` 的两种形态 `[R]`

```text
hdc -t <k> shell mkdir -p /data/local/tmp/<dir>
hdc -t <k> file send <local.hap> /data/local/tmp/<dir>/entry.hap
hdc -t <k> shell bm install -p /data/local/tmp/<dir>        # 目录形 → install bundle successfully.
hdc -t <k> shell bm install -p /data/local/tmp/<dir>/entry.hap -r   # 单文件形 → install bundle successfully.
```

**两种形态在 OH 3.2 上都成立。** 目录形不是单包安装的必要条件 —— ArkDeck 现在
用的单文件 `-r` 形对单 HAP 是正确的,不必改。目录形的价值在**多包**(entry +
feature 必须同目录、一条 `bm install -p <dir>`),而 ArkDeck 的 `debug.hap@1`
input 只接受一个 `hapArtifactLease`,**多包支持是 Catalog 的 input 面变更**,
不是 lowering 能补的。故 D5 从"待真机证据"转为"需契约或 Catalog 变更"。

`file send` 的成功串本窗口一并确认:`FileTransfer finish, Size:1512003, File count = 1, ...`。

自然会产生,不必为此单独造崩溃。

## 计划外:`debug.hap@1` 真机首跑打出 D2 的 bug

`arkdeck agent run --operation debug.hap@1`(executor=agent,自动 E1 策略),
`job-5e666e2738243c737647aad67c1bb9f8`:

```text
verified send-hap / install-hap→package-readback / start-ability→process-readback
verified capture-diagnostics
outcomeUnknown stop-ability: process readback for com.example.waterflowdemo is ambiguous
→ waitingForRecovery
```

除 stop 外全链路真机通过。stop 卡住的原因是 #861 里我写的 `processPresence`
要求 `exitStatus == 1` 才判"进程不在",而真机实测:

```text
pidof <running>   -> exit 0, "443"
pidof <stopped>   -> exit 0, ""
pidof <nonsense>  -> exit 0, ""
```

**`hdc shell` 只回客户端退出码,远端的 1 根本不过桥** —— 也就是 D2 自己那条
教训("退出码不是证据")在我的 readback 判据里又犯了一次。该 shape 在生产上
永不出现,所以每一次**成功的** stop 都会落 `.unknown`。

修复:判"不在"改为看**空输出**,完全不看退出码;噪声(非数字 token)仍判
ambiguous。真机复验方式是 `arkdeck job reconcile`(见下),reconcile 走同一份
helper,结果:

```text
reconcile started stop-ability
reason: persist exact typed reconcile decision: confirmed completed ["postconditionPresent"]
reconciled: confirmed completed stop-ability   （outcomeUnknown: false）
```

即修复后的判据在真实 `pidof` 输出上给出了正确答案。

### `bm uninstall` 的状态串:deveco 的串在这台设备上不出现

```text
bm uninstall -n <installed>   -> "uninstall bundle successfully."      exit 0
bm uninstall -n <NOT installed> -> "error: failed to uninstall bundle." + "code:9568386"   exit 0
bm dump -n <installed>        -> "com.example.waterflowdemo:" + JSON    exit 0
bm dump -n <NOT installed>    -> "error: failed to get information..."  exit 0
```

事实表 §5 里 `uninstall missing installed bundle` 那条(源自 deveco)**在 OH 3.2
DAYU200 上不成立**。这恰好证明 D2 选择 presence readback 而不是解析状态串是对的:
若当初按串判,今天就会误判。同时 `bm dump` 的两种输出都能被 `packagePresence`
正确解析(装了→含 bundle 名;没装→错误文本不含 bundle 名)。

## 未修复的发现(留给维护者决定)

**F1 —— reconcile 结算了 job,却没有结算 capability 用量台账。**
`job reconcile` 把 stop-ability 判为 `confirmed completed`、job 的
`outcomeUnknown` 归 false,但该 capability 的 lineage 仍是:

```text
outcomeHistory: [{outcome: "outcomeUnknown", terminalState: "waitingForRecovery"}]
lineageAllowsNewExecution: false
```

于是该 target 上**所有后续自动 E1 仍被拒**(`automatic E1 target lineage is
blocked`)。这是 durable recovery 的一个真实缺口:恢复路径无法把目标恢复到可用
状态。我**没有**动它 —— 往已消费 capability 的用量台账里写 `confirmed` 属 E1
授权面,写错会削弱这道 guard,不该由 Agent 单方面改。本窗口因此**没能**跑出一次
完整绿的 `debug.hap@1`;D2 的真机证据来自直接 probe + reconcile 判定,不是一次
端到端绿跑。

**F2 —— 中途停下的 job 会遗留 provider-owned 远端文件,且无操作员出路。**
上述 job 停在 stop-ability,`cleanup-remote-staging` 从未执行,于是
`/data/local/tmp/arkdeck-job-5e666e27…-send-hap-owned.hap` 留在设备上。它**不是**
cleanup debt(debt 只在 cleanup 失败时记录,不在"从未执行"时记录),
`cleanupDebt.list/continue` 也没在 CLI 暴露。本窗口用一条人工 `rm -f` 清掉了它。
