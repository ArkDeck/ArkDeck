This supplement records the additive `runtime.tool.register` method from the
actual Swift control handler and the actual Swift CLI. The sole method input is
`{kind: "deveco", root: <absolute local path>}`. The production daemon delegates
to `BootstrapDevEcoToolchainRegistry.register`; it never selects or executes a
tool. HDC registration retains its existing Swift in-process implementation.

The current registry contains 100 methods, with contract identity
`d1a9f8d57112b45acc463fa1b84a25be77c441c49d85071d328979fea0a59b1c`.
The CLI marks this method mutation-capable: zero device dispatch does not prove

## Actual producer

`BootstrapInspectionControlContractTests` adds three registration tests. The
positive test reads the real `/Applications/DevEco-Studio.app/Contents` through
native signature and sealed-resource validation. It writes only a newly created
private temporary registry. The installed application, installed daemon and
normal user registry are not registration destinations. No candidate executable
is launched. A real local reference is attached through the existing registry
`acquire` API; repeating registration preserves that owner and all index bytes.
This is local metadata testing, not provider coverage or real-device acceptance.

The real Swift CLI connects to the temporary daemon with `--socket`, registers
the same DevEco root and returns the exact existing receipt. The test compares
registry contents before and after repeated registration and compares the
source Info.plist bytes. Native file identities, child hashes and sealed
resources are revalidated by the owner on each operation.

The observed path rules are intentionally preserved:

- Standard-root registration and its repeat return the same available generation-1 receipt.
- A trailing `/` returns the same receipt and does not change metadata.
- An internal `//` preserves a different Foundation root identity, causing
  `resourceConflict` for the already-registered content, with unchanged metadata.
- Relative paths, dot components and NUL are refused before owner access.

The first exploratory run incorrectly expected the internal `//` variant to
succeed. Its actual refusal established the behavior above; only that test
expectation was corrected. The final passing recording below is the published
producer input. No production path rule was relaxed to satisfy the assertion.

Actual negative owner cases include an invalid Contents root and a corrupt
DevEco index. The separate classified-failure test explicitly injects negative
owner errors to exercise the handler's failure mapping. Those frames are not
native-failure or hardware evidence. They retain `invalidInput`,
`fileIdentityChanged`, `resourceConflict`, `admissionDenied`, `recordUnreadable`,
`quotaExceeded`, `ioFailure` and `outcomeUnknown`; an unclassified injected error
maps to `outcomeUnknown`. Every result asserts zero device dispatch.
