### Why the `FAIL` rows are not defects

`installed-daemon-owner-image-signature-or-package` and the three `product-*` rows fail because
the daemon is unsigned (`NotSigned`) and no signer pin or package family was configured. The
client connected to the harness-started daemon and refused it for lacking a trusted signing
identity or package (not for a wrong image, the refusal the squat row shows), before sending
any frame, and the CLI
returned `runtimeUnavailable` with exit 69. That is XPA-AC-6 and design §F.2 as specified: there
is no switch that skips identity verification (design §L.1 item 22). The harness scores these
rows against the positive installed-daemon path, which needs the signed identity (maintainer
item 1). Nothing was changed to make them pass.

### Observations worth carrying forward

1. **Squat refusal surfaced as Win32 231, not 5.** Against the squatter, whose pipe is created
   with `nMaxInstances = 1`, the product's `CreateNamedPipeW(FILE_FLAG_FIRST_PIPE_INSTANCE,
   PIPE_UNLIMITED_INSTANCES)` failed with `ERROR_PIPE_BUSY` (231) — consistent with the
   instance limit being checked before the first-instance flag; this run does not isolate which
   check fired. `create_instance` in
   `arkdeck-platform/src/windows/mod.rs` rewrites only `ERROR_ACCESS_DENIED` (5) into the
   "named pipe … is held by another instance (Win32 error 5); daemon did not start" message,
   so against a one-instance squatter the daemon still fails closed but with the raw OS error,
   not that message. The CI test `second_daemon_cannot_take_an_existing_pipe_name` covers the
   product-vs-product case (both unlimited instances), which does give 5. tasks.md's fallback
   wording ("the second instance fail[s] with `ERROR_ACCESS_DENIED` and `doctor` reports the held
   name") therefore describes only a squatter that allows more instances. Recorded as a fact; no
   source change in this slice.
2. **Localized error text is mis-decoded in the record.** The OS message for 231 is Chinese on
   this host; the probe prints UTF-8, and the harness decoded the child's stdout with the
   console code page, so `daemonBind.error` in `spk3.json` is mojibake. `osError` is exact.
   Message text is parity tier T2, so no verdict depends on it; a harness that sets
   `StandardOutputEncoding` to UTF-8 would record it legibly.

## What this proves

- `GetNamedPipeServerProcessId` works on a client handle opened with `CreateFileW` on Windows 11
  10.0.26200 and returns this connection's server PID. Layer 2 of the client-side server
  authentication (tasks.md XPA-002 "Client-side server authentication", design §F.2) is
  available; the "fail flips the boundary statement" branch (r5) does not apply, and the
  boundary statement stands as written.
- Non-elevated, the product client refuses a same-account pipe served by a different image and
  refuses the product daemon image when it has no trusted signature or package, each before any
  frame (`framesSent: 0`, squatter `receivedBytes: 0`); the CLI surfaces that as
  `runtimeUnavailable`, exit 69, with schema-valid envelopes.
- The product listener refuses to bind a name already held by a same-account squatter.
- `VerifiedTool` argv/environment/output-limit/timeout behaviour holds on this host.
- The Windows pipe transport's native tests pass on real Windows hardware, with the latencies
  above.
