# SPK-4 — WinUI 3 gate on the Windows 11 x64 reference host, 2026-09-30

Spike SPK-4 (`tasks.md` spike table; design §H.4 criteria (a)–(e), §H.5, §H.6, §I.2 UI rows):
pass = all of (a)–(e) pass; fail = any fails and cannot be fixed in two weeks, then WPF (.NET 10
Fluent). Fixture pages only: no daemon, ClientKit, device or Runtime record is involved, and no
result here is product, platform or real-device acceptance (§H.5, §H.6 item 4). Preparation:
`spk-4-prerequisites-crib-20260930.md`; the maintainer answered its open questions (CLI only, no
Visual Studio; alpha WinUI templates accepted; Windows App SDK 2.5.1; spike under `windows/**`).
After this run the maintainer ruled that the Windows support tuple is Windows 11 x64 only (ARM64
deferred, proposed as CHG-2026-074 r13), which changes the ARM64 half of (d) to "not required".

**Verdict: WinUI 3 go (provisional).** No criterion failed. (a) and the automated part of (c) pass;
(b) passes on every measured launch; (d) passes the x64 build, self-containment and size checks;
the clean-host install, the cold-after-reboot start, Narrator by ear, the keyboard path and (e)
need the maintainer (list at the end) and turn the verdict final. The WPF fallback is not
triggered and was not built.

## What was built

`windows/spikes/spk4/` (this PR), C#, .NET 10, Windows App SDK 2.5.1 self-contained:

| Project | Role |
| --- | --- |
| `ArkDeck.Spk4` | WinUI 3 shell scaffolded with `dotnet new winui-navview`, then cut down: Mica (Base) backdrop, `TitleBar` with `ExtendsContentIntoTitleBar`, `NavigationView` with six fixed items (Overview, History, Viewer, Job Inspector, Debug, Trace) plus the built-in Settings item, `InfoBar` for state, Segoe UI Variable / Segoe Fluent Icons, system light/dark/high-contrast and accent. History = virtualised `ListView` of 10,000 rows (compiled `x:Bind`); Viewer = `TreeView` of 20,000 nodes, all expanded; Job Inspector = fixture Job whose state text is a UIA live region (`LiveSetting=Assertive`, `LiveRegionChanged` raised on each change); Debug (five `SelectorBar` tabs with the macOS names) and Trace show `unavailable(notImplemented)` plus the CLI path from `cli-feature-coverage.json` and a working "Copy CLI command" action — no disabled placeholder control (XPA-AC-8). A fixture banner states that no daemon is connected. `--bench <dir>` runs the scripted benchmark. |
| `ArkDeck.Spk4.Fixtures` | UI-free fixtures (History rows, Viewer tree, fixture Job states), frame statistics, stable AutomationIds, the unavailable-capability catalogue |
| `ArkDeck.Spk4.Tests` | MSTest, 14 tests: token mapping drift (independent parser), HighContrast = system colours only, fixture sizes, percentile/§H.4 (a) threshold, state never colour-only, cancel availability, nav AutomationIds, no `IsEnabled="False"` and no literal colour in app XAML, CLI paths match the coverage file |
| `ArkDeck.Spk4.Probe` | Out-of-process UIA runner (UIA3 COM through FlaUI): startup timing, tree walk, live-region events, keyboard path, layout bounds |
| `tokens/gen_xaml_tokens.py` | Generates `ArkDeck.Spk4/Themes/ArkDeckTokens.xaml` from `docs/design/arkdeck-ds/src/tokens.css`; `--check` fails on drift |
| `scripts/measure.py` | Runs the benchmark and the probe and writes a summary |

Token mapping (one palette, no second one): every colour role of `tokens.css` becomes
`ArkDeck<Role>Color`/`Brush` in the Light and Dark theme dictionaries, values verbatim
(`rgba` alpha → `#AARRGGBB`); in HighContrast every brush maps to a Windows system colour and all
state colours map to the window text colour, so state is carried by glyph + text
(AC-UX-005-01). Spacing, radii and the type ramp map 1:1 (CSS px = WinUI effective px); fonts map
to Segoe UI Variable Text and Cascadia Mono/Consolas (§H.1 allows platform fonts); the two shadow
tokens are not mapped (WinUI elevation replaces them). Surfaces use WinUI's card/layer brushes so
Mica shows through — `tokens.css` panel colours are opaque web stand-ins (its header, spec v0.8 §2).
WinUI controls keep the system accent, per the maintainer's direction; the token accent is
exported as `ArkDeckAccentBrush` but not applied to controls (open point below).

## Results per criterion

### (a) List virtualisation — **PASS**

In-app benchmark, release, unpackaged self-contained x64, 5 independent process runs, 600 frames
per pass. Frame time = interval between `CompositionTarget.Rendering` callbacks (UI-thread frame);
the scroll is driven by `ScrollViewer.ChangeView` every frame (the same path UIA `ScrollPattern`
uses). "Steady" = 48 px/frame (≈ 2,900 px/s, a fast wheel/drag scroll); "page jump" = one full
viewport per frame (≈ 45,000 px/s, a stress mode far beyond any user scroll, reported for margin).

| Surface | Mode | p50 (ms) | **p95 (ms)** | p99 (ms) | max (ms) | frames > 33 / > 100 ms (of 3,000) |
| --- | --- | --- | --- | --- | --- | --- |
| History, 10,000 rows | steady | 16.68 | **16.79–16.86** | 16.92–19.34 | 17.4–27.0 | 0 / 0 |
| History | page jump | 19.7–31.2 | 23.4–**39.9** | 25.0–46.2 | 33.2–59.5 | 236 / 0 (226 in one run) |
| Viewer, 20,000 nodes | steady | 16.68 | **16.78–17.00** | 16.96–21.99 | 17.2–32.8 | 0 / 0 |
| Viewer | page jump | 16.7–18.7 | 24.0–30.6 | 88.6–93.0 | 98.8–165.3 | 53 / 11 |

Ranges are across the five runs. Fail threshold p95 > 33 ms: steady scroll is at the display
frame time in every run; the stress mode stays under 33 ms in 4 of 5 History runs and all Viewer
runs. An `x:Phase` variant of the History row did not improve the stress mode (5 runs, p95
27.6–43.6 ms) and was not kept; run-to-run spread in that mode suggests host noise (locked session,
other agents' processes). §I.2's "no main-thread stall > 100 ms" holds for steady scroll; the
Viewer stress mode had 11 such frames.

Load and memory (same runs):

| Surface | Fixture | Bind → rows on screen | Working set / private after scroll |
| --- | --- | --- | --- |
| Shell at first frame | — | — | 108.6–110 / 41.2–43 MiB |
| History | 7–10 ms | 62–88 ms | 159.7–166.3 / 94.2–100.8 MiB |
| Viewer | 3 ms (model) + **1,356–1,814 ms** building 20,000 expanded `TreeViewNode`s | 199–326 ms | 248–251.8 / 185–188.3 MiB |

Finding for TASK-XPA-020 (not a §H.4 criterion): a fully expanded 20k-node `TreeView` costs
≈ 70–90 µs per node on the UI thread (post-order and pre-order expansion measured the same).
§I.2's proposed Viewer "build ≤ 500 ms" (拟) cannot be met that way; create child nodes on
`Expanding` (`HasUnrealizedChildren`) or render the flattened tree in a virtualised list.

### (b) Cold start to interactive — **PASS on measured launches; cold-after-reboot NOT_RUN**

Probe: t0 = before the launch call; t1 = UIA exposes `Nav.Overview` enabled and on screen. 10 runs
per series, 1.5 s apart, each process closed by the probe.

| Target | Series | median (ms) | **p95 (ms)** | max (ms) |
| --- | --- | --- | --- | --- |
| Packaged: the published MSIX's contents registered as a development package, AUMID activation | 1 (first run = first launch after registration: 697.9) | 496.8 | **697.9** | 697.9 |
| Packaged | 2 | 534.6 | **592.7** | 592.7 |
| Unpackaged self-contained publish (`WindowsPackageType=None`) | 1 | 439.0 | **697.7** | 697.7 |

In-app first frame after process start: 338–439 ms (5 bench runs). Threshold 2 s. An earlier
series against a non-ReadyToRun, untrimmed `dotnet build` layout had a 3,207 ms first launch after
registration (then 661–780 ms): ship only the published (R2R + trimmed) bits. Not covered: first
launch after a reboot (file cache cold) — the host was not rebooted.

### (c) UIA / Narrator — **PASS (automated); Narrator by ear and keyboard path NOT_RUN**

`ArkDeck.Spk4.Probe uia`, packaged and unpackaged, same results:

- Six fixed navigation items, each one `ListItem` with `SelectionItemPattern`, keyboard
  focusable, enabled, stable `AutomationId` (`Nav.Overview` … `Nav.Trace`) and name; the Settings
  item is `SettingsItem`. Selecting each through UIA reaches the page's primary surface.
- History `List` exposes rows by name (`job-000001, artifact.export, Unknown, 2026-09-30 09:00:00`);
  Viewer exposes `TreeItem`s with `ExpandCollapse` state; the Debug and Trace notices are
  `StatusBar`s named `Artifacts: unavailable(notImplemented)` / `Trace Viewer: unavailable(notImplemented)`
  with the CLI path as text and an enabled "Copy CLI command" button.
- Job state: `Job.State` has `LiveSetting = Assertive`; four scripted state changes produced four
  `LiveRegionChanged` events carrying `Job state: Running`, `Waiting for you`, `Running`,
  `Succeeded`. Cancel is hidden with a stated reason once the Job has ended.
- No visible disabled button on any page.
- `InfoBar` exposes no UIA name of its own; the spike sets `AutomationProperties.Name` (a
  pattern XPA-007 must keep).
- Keyboard: NOT_RUN — `SendInput` fails on the locked session (Win32 error 5). The probe's
  keyboard step (focus `Nav.Overview`, Down ×3, Enter → Job Inspector, Tab ×2) runs as is on an
  unlocked desktop.

UI runner decision input (§H.6): FlaUI/UIA3 from a .NET console worked for the tree, patterns,
properties and events even with the session locked, and cleans up by PID. `winapp ui` 0.7.0
connected (`status`, `search` found `Nav.JobInspector` by its AutomationId) but refuses `focus`
and `send-keys --via send-input` without an interactive desktop, and its default `post-message`
transport does not reach WinUI's windowless controls. Recommendation for XPA-007: UIA semantic
tests through a small FlaUI-based adapter; `winapp ui` for agent-side inspection and screenshots.
WinAppDriver is not needed.

### (d) Build and self-contained install — **x64 build PASS; install on a clean host NOT_RUN; ARM64 not required (r13: x64 only, ARM64 deferred)**

- `dotnet publish -c Release -p:Platform=x64 -p:GenerateAppxPackageOnBuild=true` →
  `ArkDeck.Spk4_0.4.0.0_x64.msix`, **61,444,569 bytes (58.6 MiB)**, 352 files, unsigned
  (`AppxPackageSigningEnabled=false`). §I.2 proposed budget: MSIX self-contained ≤ 150 MB.
- Self-containment: the package manifest has no `PackageDependency` (no Windows App Runtime
  framework package); the unpackaged self-contained folder is 150,602,979 bytes, 254 files.
- The MSIX contents registered per user as a development package (Developer Mode, loose layout),
  launched, passed the UIA walk, and were unregistered. This host already carries Windows App
  Runtime 2.2–2.5, so this is not the clean-host proof.
- Signed install (`Add-AppxPackage` of the `.msix`) NOT_RUN: needs the maintainer's development
  certificate (crib §4 step 6). Clean-host install NOT_RUN: needs Windows Sandbox or a clean VM
  (crib §4 step 7).
- Informational (not required under r13): `-p:Platform=ARM64` builds an ARM64 MSIX of 59,738,519
  bytes; not launched.
- Size note for TASK-XPA-022: the `Microsoft.WindowsAppSDK` 2.5.1 metapackage brings AI/ML/Search
  components into the self-contained output (`onnxruntime.dll` 21.7 MB, `DirectML.dll` 18.7 MB,
  `Microsoft.Windows.Search.dll`, …) that the app does not use; referencing only the component
  packages it needs should shrink the package substantially (not tried here).

### (e) High contrast and text scaling — **NOT_RUN (system settings); prepared**

Turning on a contrast theme or 225 % text size changes the maintainer's per-user settings, which
this run may not do. Prepared and checked instead:

- HighContrast theme dictionary uses only system colours, state is glyph + text in every row and
  in the UIA names (tests above; probe output).
- Layout probe at the current settings (high contrast off, text scale 1.00, 1280×860 window):
  0 elements outside the window, 0 empty bounds, 0 overlapping navigation items on every page
  (one run caught one transient overlap during the selection animation).
- WinUI text controls honour the system text-scale factor by default; nothing in the spike
  disables it.

## Other findings

1. `dotnet new winui-navview` / `winui-unittest` hung indefinitely in the post-creation restore
   (no child process, killed after several minutes); a separate `dotnet restore` completed in 18 s.
2. The `winui-unittest` template produces a packaged WinUI test app; `dotnet test` without
   Visual Studio's deployment fails with `REGDB_E_CLASSNOTREG` (no package identity) and
   `UITestMethodAttribute.DispatcherQueue` null. The spike uses a plain MSTest project plus the
   out-of-process UIA probe instead.
3. The NavigationView's built-in strings follow the app's resource language: the unpackaged run
   showed the OS language for "Settings", the packaged run (manifest default language) showed
   "Settings". XPA-007 must set the language explicitly from the shared bilingual source
   (AC-I18N-001).
4. Trimming reports IL2104 warnings for `Microsoft.Windows.SDK.NET` and `WinRT.Runtime`; the trimmed
   build ran every flow above. The MSIX tooling warns that `mspdbcmf.exe` is missing (no symbols
   package without the VS component).
5. Open point for the maintainer: should WinUI controls use the product accent from `tokens.css`
   (`#006edb`/`#58a6ff`) instead of the Windows accent? The spike follows the direction "system
   accent" and keeps the token accent available.

## How to reproduce

From `windows/spikes/spk4`, Git Bash, NuGet cache on D: (`NUGET_PACKAGES`):

```sh
python tokens/gen_xaml_tokens.py --check
dotnet build spk4.slnx && dotnet test spk4.slnx
# (a), unpackaged self-contained release
dotnet publish ArkDeck.Spk4 -c Release -p:Platform=x64 -p:WindowsPackageType=None -o out/unpackaged-x64
dotnet build ArkDeck.Spk4.Probe -c Release
# (d) MSIX; (b)/(c) packaged: register its contents as a development package (Developer Mode)
dotnet publish ArkDeck.Spk4 -c Release -p:Platform=x64 -p:GenerateAppxPackageOnBuild=true -p:AppxPackageDir=<abs>/out/msix-x64/
#   extract the .msix to out/msix-x64-layout, then in PowerShell:
#   Add-AppxPackage -Register out\msix-x64-layout\AppxManifest.xml   (Remove-AppxPackage afterwards)
python scripts/measure.py --exe out/unpackaged-x64/ArkDeck.Spk4.exe \
  --probe ArkDeck.Spk4.Probe/bin/Release/net10.0-windows10.0.26100.0/win-x64/ArkDeck.Spk4.Probe.exe \
  --aumid 'ArkDeck.Spk4_jj88tn1d1ahgg!App' --out out/run
```

`out/`, `bin/` and `obj/` are ignored (`windows/.gitignore`). Screenshots were taken for review
only and not committed: the Overview page shows the Mica window with the custom title bar
("ArkDeck · SPK-4 fixture", pane toggle), the navigation pane with the six items and Settings,
the blue "Fixture data" InfoBar, and two rounded cards (current target; latest jobs with a state
glyph, monospace Job id, operation and state text per row).
