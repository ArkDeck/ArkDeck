# SPK-5 — NTFS durability primitives on the Windows 11 x64 reference host, 2026-09-30

Spike SPK-5 (tasks.md spike table; design §J.3, risk R7): `FlushFileBuffers`, `MoveFileExW`
write-through, `LockFileEx`, the torn-tail exhaustive test; pass = torn-tail matrix passes and
append p95 recorded; fail = atomic replace cannot be proven; unlocks the TASK-XPA-005 write path.
Host facts only: no Runtime store, device, capability or journal decision is involved, and no
result is product or platform acceptance.

**Verdict: go.** The torn-tail matrix passes, append p95 is ≈ 1 ms against the 10 ms budget,
and atomic replace is proven — with POSIX-semantics rename, not with `MoveFileExW` (below). The
Windows write path must follow the five design consequences at the end of this record.

## How it was run

- Probe: `rust/crates/arkdeck-platform/examples/windows_spk5.rs` (this PR), Windows-only; the
  non-Windows build prints `Windows only` and exits 2.
- `cargo build --release -p arkdeck-platform --example windows_spk5`, then
  `windows_spk5.exe all <work-dir>`; `all [--journals N] <dir>...` bounds the exhaustive matrix.
- Host: Windows 11 Pro 10.0.26200 x64, i7-10700 (8C/16T), one 1 TB NVMe SSD; the W0 record is
  `evidence/runs/TASK-XPA-002/windows-host-w0-20260930-run.md`. Non-elevated, UAC on.
- Work directory measured: an NTFS directory on D: inside the Defender path exclusion
  (`rust\target`), started 10:19, finished 10:22 local time, with no build running.
- Torn-tail input: the recorded Swift Journals in `rust/tests/fixtures/**` (each `.jsonl`
  whose first record is `jobCreated`, the selection `job_journal_replay`'s own fixture test
  uses): 492 available, 17 sampled evenly; the repair rule is `ReplayState::replay`'s split
  (the durable length ends at the last LF; the rest is a torn tail).

## Not covered

- **Power loss and OS crash.** A process kill leaves the file cache intact, so only write
  ordering is tested; NTFS may expose a zero-filled extension after a power loss when the file
  size was extended but the data was not yet written. The Runtime's rule (bytes after the last
  LF are a torn tail, never interpreted) and the record decoder's refusal of a malformed
  complete line are what protect against that; SPK-5 does not prove it.
- **Other volumes and a scanned path.** A second run on an NTFS directory outside the Defender
  exclusion and on the system volume (where the product state root `%LOCALAPPDATA%\ArkDeck\Agentd`
  lives) did not finish within the tool's background time limit — the exhaustive matrix is
  roughly eight times slower under real-time scanning — and later ran concurrently with builds,
  so no numbers from it are recorded. Follow-up: rerun `windows_spk5 all --journals 4` on the
  system volume on a quiet host.
- ReFS / Dev Drive, removable volumes, network shares: not tested (not supported state roots).

## Consequences for the TASK-XPA-005 write path

1. **Atomic replace = POSIX-semantics `FileRenameInfoEx`, not `MoveFileExW`.** `MoveFileExW`
   cannot replace a file any reader holds open, which the Runtime's readers do. Every handle the
   Runtime opens on a replaceable file must include `FILE_SHARE_DELETE`; a handle without it
   makes the replace fail closed (32), never silently succeed.
2. **Locks only on dedicated lock files.** `LockFileEx` is mandatory and per handle: the lock
   file must never be read or written through another handle while locked (lock a range beyond
   end-of-file if the file carries any bytes), and one process must not take the same lock
   twice through two handles.
3. **Directory durability needs a GENERIC_WRITE directory handle** — the namespace barrier that
   Unix gets from `fsync(dirfd)`; it costs ≈ 0.2 ms per append.
4. **Identity = `FileIdInfo`**, where Unix uses (dev, ino); a replace moves the source's id to
   the target, exactly like `rename(2)`.
5. **The torn-tail rule ports unchanged**: every observed crash state was a byte prefix, so the
   existing replay split and truncate-to-durable-length repair (`SetEndOfFile` +
   `FlushFileBuffers`) are correct on NTFS for process death. Mitigation R7's "dual-file
   alternation" is not needed.
