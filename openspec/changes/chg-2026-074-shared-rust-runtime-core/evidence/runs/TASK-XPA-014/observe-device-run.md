## Behaviour

- **HDC typed actions** (`arkdeck-provider-hdc/src/operation.rs`, lane A's operation part): Swift
  `HDCObservationProviderAdapter`'s closed vocabulary for this operation — `-v`, `checkserver`,
  `list targets -v` and `-t <connectKey> shell param get const.product.name|const.ohos.fullname`,
  15 s each — with its receipt judged as Swift judges it (the observation parsers already ported,
  `param get`'s echoed key stripped, the target row confirmed by the bound key, state and
  identity), the exact persisted action a Job record keeps before its intent, and the `HdcDispatch`
  seam an executor implements. `FixtureDispatch` runs a pinned executable through
  `VerifiedTool::run_read_only`; lane B's `run_tool` (#1915) replaces it for a registered HDC.
- **Target facts** (`device_facts.rs`): Swift's standalone daemon `TargetStoreFactsPort` — the
  adopted record's route (a Target routed through an alias is refused, since Swift consults a live
  candidate observation this owner does not hold), the identity its connect key names and the
  configured executable's digest — and the engine's `validateEvidenceFacts`.
- **Plan and admission** (`job_plan.rs`, `job_admission.rs`): the device-bound branch of
  `materializeTypedPlanBeforeAuthorization` — a registered provider, the Artifact store, the facts
  checked against the request, every step as the engine or the provider materializes it — whose
  plan document binds the Target identity and revision; the admitted record keeps both.
- **Run** (`device_run.rs`): `runOwned` over `executeSteps` and `dispatchWithWAL`: facts resolved
  again for every device step, the exact typed action persisted before the write-ahead intent,
  the executor started only after it, the receipt verified, the correlated outcome, the evidence
  preflight in its required order and the observation it becomes, `tool-facts.json`,
  `device-facts.json` and `binding-snapshot.json` published after their steps, and Swift's lanes
  for a failed step, an unknown outcome (parked, intent outstanding, never replayed), a publication
  failure and a cancellation at a step boundary.
- **Session and reads** (`session_publication.rs`, `job_result.rs`, `job_record.rs`): Swift
  `deviceContext` — a device Session only from the Job's own verified observation, confirmed
  Journal device outcomes that agree with it and its admission audit — and the evidence
  observation in `job.evidence` and `job.result`.
- **Development HDC** (`arkdeck-agentd`): `ARKDECK_DEVELOPMENT_HDC_PATH`, only with
  `ARKDECK_DEVELOPMENT_STATE_ROOT`, names the fixture executable, pinned by its digest at startup.
  A registered HDC executable (either published macOS identity) is refused: it would address a real
  server and device. `ARKDECK_HDC_PATH` stays refused in isolated mode.

## Shared oracle

`rust/tests/fixtures/observe-device/` is recorded by Swift
`ObserveDeviceOracleContractTests.testSwiftObservesTheSharedFakeDevice` in the oracle PR. The
oracle composes the standalone daemon's engine in-process (the production daemon refuses an
unregistered HDC executable) with the daemon's facts port, its Session publication writer and the
shared fake: one POSIX sh driver at `/private/tmp/arkdeck-hdc-oracle/hdc` (`HDCOracleFake`, the same
bytes for every HDC oracle and every Rust replay, because the tool's digest is part of a Job's
evidence) answering from the oracle's `hdc-answers.sh`. Four Jobs run over one store — one
observes the device, one meets a server of another version, one finds another device's row, one
gets no version and parks — and three requests are refused before admission (a stale revision, no
revision, a target never adopted); a second run of the observed Job is refused; every Job's result,
evidence and Artifact list are read last.

## Deliberate differences from Swift

- The isolated owner runs a fixture HDC only; a registered one is refused until the Rust owner
  holds the server identity proof in its dispatch (#1914's lease, #1915's runner).
- Swift keeps a session-scoped carriable readback and the latest succeeded observation in memory;
  neither is kept, so every run reads the device again.
- A cancellation is honoured at the next step boundary, as Swift's step loop honours it for HDC
  steps, whose cancellation is not immediate.
