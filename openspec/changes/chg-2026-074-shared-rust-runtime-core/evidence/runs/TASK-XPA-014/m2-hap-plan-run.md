## Production scope

`job.plan` alone accepts `debug.hap@1`. It resolves entry and additional leases
against exact Target, binding revision and identity; retains Import input holds;
and lowers the typed HAP Provider into the complete success and failure plan.
The historical unpublished `cfffc029` was consulted for journal argument shapes,
not imported for admission or capability policy.

The foundation now carries the owner-validated primary Artifact facts in
`Materialized`: exactly `artifactId`, `artifactSha256`, `artifactByteCount`, all
strings. Byte count comes from validated integer metadata and is rendered with
canonical decimal `to_string()`. It is never a caller-supplied string or generic
JSON number. Additional packages keep their own exact leases and ordered plan
lowering; Swift does not add them to the primary facts map.

The existing admission query uses materialized facts; the fresh consumption
query uses freshly materialized facts. Existing Runtime policy fingerprinting
sorts fact keys and includes their values. The capability store's separate
consumption fingerprint does **not** independently hash Artifact facts in Swift
or Rust; that algorithm is unchanged. Empty HAP facts cannot be generated by
successful HAP materialization, and the closed admission allowlist prevents
issuing HAP capabilities before the complete runner is implemented.

The shared step-set digest encodes requested success steps in Catalog order,
then compensations in reverse source order: stop-ability, cleanup-uninstall,
cleanup-remote-staging. Each compensation uses its `compensation-` row identity.
Retain policy omits uninstall compensation; running success policy still keeps
stop compensation. Planning and correlation reuse the same selection helper.
Consumption correlation carries the primary `artifactSHA256` when present.

Historical HAP record decoding requires the Artifact digest and, for the current
Catalog only, recomputes the complete step-set digest. Existing reservation,
plan, binding, ordinal and request checks remain. This is not proof that a
well-formed historical Artifact digest names actual bytes: future execution
must re-read the immutable owner and compare fresh authority/ledger correlation.
No historical evidence grants permission to replay an unknown intent.
