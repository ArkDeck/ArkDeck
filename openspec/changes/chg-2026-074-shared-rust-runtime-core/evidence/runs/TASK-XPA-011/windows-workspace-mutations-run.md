# TASK-XPA-011 — Windows workspace mutations on Runtime-owned copies (WM3 GJ-5, PR 5), 2026-10-04

- Task: TASK-XPA-011, WM3 slice GJ-5, fifth layer, stacked on the lanes layer
  (`agent/xpa-011-windows-workspace-lanes-20261004`). The installed (account) Windows daemon applies a
  patch to a Runtime-owned copy, checkpoints the copy and reverts the patch. It uses the code-owned
  patch (the daemon's own image) and the trusted `System32\tar.exe`, under the Runtime's own
  capability for the copy, as the macOS production daemon does (`workspace_patch_process.rs`).
- Base: the head of the lanes layer.
- Host: the Windows 11 x64 reference host, non-elevated. Each daemon ran over a fake account
  (`USERPROFILE` naming a fresh directory below the temporary directory). Nothing of the real
  account's was read or written apart from its single-instance guard and pipe, which the tests
  check are free. No HDC, device, DevEco or credential was used.

## Correction: no daemon outlives the test on the account's pipe (2026-10-04)

A daemon started from this test's signed copy (`ad-signed-workspace-…`) was found serving the
account's real pipe after a run. The most likely cause is that the CLI's own client start
launched the daemon it had been pointed at while that daemon's pipe was briefly absent.
Neither test can do that any more:

- Each test now holds the account's daemon starters' turn (`StarterLock`, as
  `windows_account_locations_process.rs` does) for as long as it runs. A CLI that finds the
  pipe absent waits for the turn instead of starting the daemon, and no other process starts
  one over its own fake account meanwhile.
- Each test ends by asserting that no daemon serves the account's pipe.
- The test's own daemons are stopped by their stop request, or killed and waited for by their
  drop on any failure.
