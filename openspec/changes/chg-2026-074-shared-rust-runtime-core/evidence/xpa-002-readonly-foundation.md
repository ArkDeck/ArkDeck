## Delivered path and current limits

The workspace has seven crates: `arkdeck-contract`, `arkdeck-platform`,
`arkdeck-control`, `arkdeck-provider-hdc`, `arkdeck-client`, `arkdeck-cli` and
`arkdeck-agentd`. The CLI's `doctor`, `operation list` and `device candidates`
use an authenticated local connection, verify health on that same connection,
and enter transport-free handlers. The current device wire method is
`device.observations`; `device candidates` is the CLI projection. Generated
types and validation consume the current method registry and schema corpus.
Lost exchanges do not reconnect or replay.

The [control handlers](../../../../rust/crates/arkdeck-control/src/lib.rs)
report every Catalog operation as `unavailable` with `provider_not_registered`.
This foundation has discovery and diagnostic code, but no registered operation
execution provider. `doctor` reports that limitation; listing Catalog entries
does not advertise a working operation or a passed Golden Journey.

The [HDC provider](../../../../rust/crates/arkdeck-provider-hdc/src/provider.rs)
requires an exact registered platform/tool digest and an already-existing server
identity lease before executing its closed `list targets -v` argument array.
It revalidates the lease before publishing parsed observations. The provider
does not start or repair a server, turn an unknown observation into an empty
snapshot, accept caller-selected arguments, or create device authority.
The current tool registry contains macOS tuples only, so Windows tool selection
is unavailable. The macOS commandless server identity lease is not implemented;
that missing proof prevents every HDC dispatch on the shadow path as well.

The [platform boundary and SPK-3 instructions](../../../../rust/crates/arkdeck-platform/README.md)
describe UDS permissions and peer checks, Windows pipe identity, retained process
and executable handles, bounded process execution, and native test setup.
Windows server-PID lookup failure refuses the connection before frames; no
fallback is enabled. The probe script and cross-compilation provide implementation
tools, not evidence that the Windows-specific APIs passed on a supported host.

The current [OpenHarmony integration profile](../../../integrations/openharmony/profile.md)
and [integration lock](../../../integrations/INTEGRATION-PROFILES.lock.yaml)
do not publish a Windows HDC observation tuple. XPA-002's Allowed paths cover
`rust/**` and Windows platform documentation but do not include either of these
exact integration files:

- `openspec/integrations/openharmony/profile.md`: reviewed Windows tool/version,
  output-family and provenance registration, without borrowing macOS authority.
- `openspec/integrations/INTEGRATION-PROFILES.lock.yaml`: the matching version and
  registry/resource hash closure.

A subsequent registration change needs an explicitly scoped task covering those
files and the precise Windows registry, sanitized resource/receipt and contract
test paths selected after actual sampling. Existing
`openspec/integrations/openharmony/device-observation-probes.yaml` and
`openspec/integrations/openharmony/supervisor-observation-probes.yaml` are separate
macOS registrations; their authority cannot be relabeled as Windows evidence.
Any change to those registries or their bundled fixture copies also needs its
exact paths in that task. This delivery edits none of those files and adds no
Allowed path. A fixture executable, an unreviewed hash or a caller-supplied
version cannot satisfy the missing Windows registration.
