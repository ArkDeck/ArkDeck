# Flashing backwards to 7.0.0.34, and re-running every journey on it (2026-08-06)

## Why a second build, and why an older one

[gj4-flash-any-build-2026-08-06.md](gj4-flash-any-build-2026-08-06.md) claimed the product
can flash a build it has never seen, on the strength of one run: `7.0.0.36` → `7.0.0.37`,
newer to newer. A version derived from the archive and a version compared against a
compiled-in list behave identically in that direction. Going **backwards** does not.

`7.0.0.37` → `7.0.0.34` succeeded on attempt 1 of 16, with no code change.

- Baseline: `main@7005a8c7`
- Catalog digest: `e2f8eb6592aaeeec37c63a01708db2325b38c798b0f8272228ba0fccc2cfd0aa` (unmoved)
- Target: `TGT-958780b2ffb7`, binding revision `2` (unchanged by the flash)
- Archive: `36eaabfec0efb4785732a7fb52aab198f9f5f9cd21473f9b7c0d4d45cdf02def`, 731,180,594 bytes
- Campaign: `ECAMP-D12BD2D404FB21842C1D0B95`, job `job-08c94db0c27385403e5416d475890194`

```
verify-image-bundle  build=OpenHarmony-7.0.0.34  sha256=36eaabfe…
verified enter-loader-mode / wait-loader-disconnect / wait-loader-reconnect
verified rebind-loader-identity / flash-partitions / verify-flash-readback
verified reboot-device / wait-for-hdc / rebind-and-verify-build
verified capture-post-flash-diagnostics
terminal: succeeded

device: OpenHarmony-7.0.0.34    observe.device@1 readback: OpenHarmony-7.0.0.34
```

`rebind-and-verify-build` is what the direction tests. It expects the version scanned out of
the archive's `system.img`, not a bound or an ordering, so an older build satisfies it exactly
as a newer one does.

## GJ-5 took two submissions, and both are recorded

The first (`HTASK-7C12960C4B6E`) stopped at round 6:

```
evaluation      criteriaFailed
humanBlocked    patchProposalRequired
status humanRequired   e1Mutations 1   modelCalls 7   rounds 6/30
```

Every round of it carried `proposalRejected:operationNotOffered:workspace.apply-patch@1` — the
producer kept proposing to apply a patch before one was prepared, and ran out of no-progress
rounds before finding its way past that.

The second (`HTASK-E854F29E73A6`) passed:

```
DC-1-crash-signature-absent   5/5   observed 0
DC-2-application-liveness     5/5   observed healthy
DC-3-no-new-fatal-signature   5/1   observed 0
rounds 21/30   e1Mutations 6/8   modelCalls 20/40   wallClock 2622/9000
humanActions 0   decisionStale 0
promotion PROMOTION-B7546516E373, READY_FOR_NORMAL_PR, diff 4340353577e899c7…
```

Same one-line repair as on `.37`, and the same diff digest — the loop reached the same fix by
its own route.

**The honest reading is one pass in two attempts, not "GJ-5 passes on 7.0.0.34".** The second
run was launched to tell producer variance apart from something systematic about this build,
and the answer is variance: the two runs differ only in how the producer chose, and the first
one's stop is the loop's designed safe stop, not a fault. It was recorded before the second was
started, and it is not superseded by it. A journey whose success depends on a non-deterministic
producer has a success *rate*, and one sample of each outcome is what this window measured.

## Two product behaviours worth keeping, both observed here

**Preflight refused before any confirmation.** The first `flash preview` ran without
`ARKDECK_HDC_PATH` in the CLI's environment and was refused at `hdcToolAliveness`, with
`device mutation dispatch: 0` and the missing variable named. Nothing was spent — no campaign
attempt, no reservation.

**`flash plan` leaves a file in the repository.** It writes `arkdeck-flash-plan.json` into the
working tree, which is exactly the class of stray file that has twice caused `candidateRejected
("scopeDrift")` and cost a merge to clear. It was removed before executing. Worth naming
because the plan step reads as read-only and is not.

## What this window did not exercise

The `flash continue` recovery path and the reconciliation readback, again. Both attempts here
succeeded on their first try, so neither was reached — the same gap
`gj4-flash-any-build-2026-08-06.md` recorded, still open.
