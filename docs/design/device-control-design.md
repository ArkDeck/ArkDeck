# ArkDeck Device 真机操作设计

> Status：draft v1.5（design input，非 normative；2026-08-27 按当前 SwiftUI 实现回写）
> Golden Journey：GJ-1 设备观察入口、GJ-2 真机问题复现
> 交互稿：[`prototype.html?page=device-control`](prototype.html?page=device-control)
> 实现事实源：`ArkDeckApp/Features/Device/`、`DeviceLocalizable.xcstrings` 与 `Packages/ArkDeckKit/Sources/ArkDeckWorkflows/Device*.swift`。准入和外部效果仍以已发布 Catalog / Runtime contracts 为准。

## 1. 本版修正

上一版混合了目标能力与已经落地的界面。本版以当前 App 为参照，不把早期设想继续画成可用入口。

| 旧稿 | 当前实现与本版交互稿 |
| --- | --- |
| Device 内再放一层工具列表 | 直接进入画面与 Inspector，没有二级导航 |
| 默认显示模拟手机设置页、已有输入记录 | 首次进入是「尚未获取截图」，操作记录为空 |
| 持续预览、5 fps 目标、按时间判 stale | 没有预览入口；按需截图；已确认或结果未知的手势会使旧截图过期 |
| 开始／停止录屏、60 秒上限和倒计时 | 选择帧数后一次性采集，默认 40 帧；页面没有停止按钮 |
| 停止后合成 MP4 并发布 managed movie | 收回序列归档，在本机合成、读回校验 `.mov`；显示当前本地临时文件路径 |
| 输出 size、hash、duration 的结果卡片 | 紧凑显示帧数、实测 fps、缺帧、路径与三个后续动作 |
| 方向键虚拟指针、Enter 点击、Shift 滑动 | 当前 SwiftUI 没有这条输入路径；不在交互稿中伪装已实现 |
| 触点颜色区分全部结果、拖动轨迹 | 当前是橙色空心／有填充触点；结果类型由操作记录区分，没有轨迹箭头 |

本版不增加 operation，不改安全边界，也不把 HTML 演示成功当作真机成功。截图中的设备名、`TGT-DEMO-001`、帧率和路径均为显式演示数据。

## 2. 命名、图标与布局

- 中英文统一使用 **Device**。Sidebar 顺序为 Flash、Debug、Viewer、Trace、Device、Diagnostics；History 位于记录分组。具体设备行仍打开设备详情，不等于 Device 工作区。
- SwiftUI 使用 SF Symbol `iphone`；原型使用相同语义的线框设备轮廓。Overview 返回入口、History 分类图标与 Sidebar 保持一致。
- 标题栏只显示 Device。内容顶部左侧为设备名和 `target · binding rN`，右侧只有「获取截图」。分辨率在获得画面后出现在页脚。
- 工作区可用宽度 **≥880 pt**：画面占剩余宽度，Inspector 固定 **320 pt**；两侧以分隔线连接，不包成多张卡片。
- 可用宽度 **<880 pt**：画面高 **420 pt**，下面接 Inspector，整体可滚动。断点针对内容区宽度，不是整个浏览器窗口。
- Inspector 从上到下为操作方式、录屏、操作记录、性能提示。页脚显示画面年龄／尺寸和静止画面边界。

```text
Device
├── 设备名 / target · binding                         获取截图
├── 画面（首次为空）                       │ 操作方式
│                                         │ 录屏：40 帧 + 录制
│                                         │ 操作记录
│                                         │ 不会自行取帧 / 负载提示
└── 画面年龄与尺寸                        静止画面 / 不重发边界
```

原型窗口外的状态、语言、外观选择器仅用于评审。窗口底部另有持续可见的「交互稿 · 演示数据」说明，不属于 App 控件。`page=tools` 旧链接仍转到 Device；`page=device` 保持设备详情语义。

## 3. 截图与输入

### 3.1 截图

初次进入不自动抓图。已接管且唯一可确定的目标显示「获取一张截图后即可在其上操作设备。」；没有唯一目标时显示「无设备」，禁用截图按钮并解释不会猜测目标。

点击「获取截图」后按钮变成「正在获取截图…」并禁用。通过 `capture.diagnostics@1` 的 screenshot 选项返回画面后，按真实宽高等比显示，清除旧触点与 stale，并添加「已获取截图」记录。画面外的留白不参与坐标映射。HTML 使用标为「演示截图」的 720×1280 示意内容，不绘制虚假的系统设置页或手机外壳。

失败时保留上一张图和原来的 stale 状态，失败原因进入操作记录；没有上一张图时，原因显示在空态说明中。失败不会生成替代画面，也不会自动重试。

### 3.2 一次手势与画面失效

当前 App 使用 `DragGesture(minimumDistance: 0)`，一次完整按下／松开序列只归类为一个输入：

| 手势 | 分类与边界 |
| --- | --- |
| 移动 <6 pt，按住 <500 ms | `input.tap@1`，落点锚定按下位置 |
| 移动 <6 pt，按住 ≥500 ms | `input.long-press@1`，时长限制 500–2000 ms |
| 移动 ≥6 pt | `input.swipe@1`，起终点来自画面内坐标；时长限制 80–2000 ms |

坐标基于等比缩放后的图像矩形，乘以截图宽高后取整数，夹在 `[0, width−1]` / `[0, height−1]`。UI 不提交 raw shell 或设备路径；Runtime 负责 typed admission、目标／binding 与显示事实校验。界面不能以截图年龄替代 Runtime 的 fresh facts。

按下时显示空心触点；请求未结束时不接受另一条输入。结果返回后触点有填充，但**填充不单独证明成功**，应同时读操作记录：

- **已确认**：记录结果，截图标记「已过期」。
- **结果未知**：保留 unknown，截图同样过期；没有重发按钮，不自动重放。
- **明确失败**：记录失败，原先可用截图不因这次失败而失效。
- **旧截图上再次操作**：本地拒绝，记录「未发送——这张画面已经过期」，不发出新请求。

只有用户重新获取截图才恢复该图的输入可用性，不做操作后自动截图。失效不是旧稿的 800 ms 年龄倒计时；等待本身不会把这张图改成 stale。历史截图一开始就 stale，只用于查看；需要对精确历史目标重新抓图后才可输入。

操作记录按新到旧排列，最多 40 条，显示标题、坐标／时长、结果和可用的结果细节。当前紧凑列表没有独立时间列、Job 链接或 replay 功能。

## 4. 按帧录屏

### 4.1 请求与阶段

帧数默认 **40**，范围 **2–300**，Stepper 每次增减 **10**，在边界夹紧。这里没有秒数、分辨率或 fps 选择器：设备回读速度不能由这个控件指定。当前 App 文案中的「约每秒 1.8 帧」是此前记录的硬件量级，不是性能承诺。本轮通过已发布 CLI 操作采集 40 帧，实测 **1.61 fps**、覆盖 **24.793 秒**、无丢帧；不能把不同运行的数值当成固定帧率。

```text
idle → preflighting → capturing(frames) → assembling → validating → ready
          └ refused          └ failure ──────────────────────────→ failed
```

- 「采集中 · N」的 N 是请求总帧数，不是已采集进度。没有可靠逐帧进度时不画百分比。
- `capture.screen-sequence@1` 收回 JPEG 序列归档与时间索引；本机 `DeviceRecordingComposer` 合成 `.mov`，再由 `DeviceRecordingValidation` 读回校验。
- 点击后立即进入「检查空间中 / Checking storage」，在等待配额结果前锁定帧数与录制按钮，并固定本次请求的帧数。不能在预检期间重复提交或修改请求大小；新一次预检清除上一轮「未检查空间」提示。
- 预检、采集、合成、校验四个阶段中禁用帧数和录制按钮，显示当前阶段；拒绝或失败后恢复控件。当前工作区没有「停止录制」、60 秒倒计时、Receiving 重试或设备编码入口。
- 录制不更新左侧截图，不自动启动预览，也不自动刷新截图。截图、输入与录屏仍走各自 Runtime 准入，原型不承诺并发能力。

### 4.2 空间不足与预检不可用

App 预算与 Runtime 请求一致：`max(1 MiB, floor(frameCount × 42,573 × 1.5) + 64 KiB)`。此估算来自现有 `DeviceRecordingBudget`，并不保证每张画面压缩大小相同。

- 剩余空间已知且不够：在开始前拒绝，展示需要／剩余大小与「放不下这段录屏」。若至少容纳 2 帧，提供「N 帧 放得下」。用户选择后只调整帧数、回到 idle；不会自动开录，也不删除旧制品。
- 无法读取剩余空间：持续展示「这次运行没有对它做检查」，仍可提交；Runtime 自己的存储预检继续决定能否运行。不能把没有检查写成检查通过。
- 采集、合成或校验失败：只显示原因，不提供虚假的可导出结果。

### 4.3 完成结果

结果显示实际帧数、实测 fps、缺帧数（若有）、本地 `.mov` 路径，以及「各帧按实际拍摄间距排布，不是按平均值。」。不插值制造连续性，不把缺帧隐藏成完整录像。

当前合成文件位于 App 的临时目录，不是旧稿中虚构的 managed MP4 路径；原始采集归档与本地合成文件不能混称为同一个 Artifact。

- **在访达中显示**：定位当前 `.mov`。
- **另存为…**：系统保存面板复制文件；保留原文件。
- **再录一段**：回到 idle，保留所选帧数，等待下一次「录制」。

HTML 中这两个文件操作仅说明真实 App 的行为，不打开访达、不下载占位视频，也不声称已保存。

## 5. 当前限制与安全

「不会自行取帧」及设备负载提示固定可见，不提供关闭按钮。页脚保留完整边界：「这是静止画面，不是实时预览。每个手势都是一次 typed operation；结果未知时绝不重发。」

截图和录屏可能包含敏感设备内容，默认本地处理。原型只用无真实内容的示意画面；不得把模拟结果归类为硬件证据。

持续预览、设备侧编码、键盘虚拟指针、输入轨迹、独立录屏与 Diagnostic Session 的关联均不属于当前 Device 已实现交互。键盘无法替代画面手势是当前产品的可访问性缺口，本版如实记录，不用 HTML 独有功能掩盖。未来补齐时需与产品代码、测试和设计一起更新；涉及新 operation / Provider / profile / 安全策略的变化仍遵循仓库审批规则。

## 6. 走查与参考

状态选择器支持默认空态、已截图、stale、历史只读、下一次 unknown、明确输入失败、无目标、截图失败、配额不足、配额不可读、录制失败、缺帧及 ready。每次切换只重置演示状态，旧异步回调不能覆盖新状态。

本轮补充 `deviceState=runtimeUnavailable`：预检后录屏入口被 Runtime 拒绝，显示失败且不进入采集／合成／ready；没有视频可导出。此场景来自本轮真机 App 走查发现的部署缺陷，仍用显式演示数据呈现。

1. 默认没有画面、没有输入记录，录屏为 40 帧。
2. 获取截图后操作一次：pending → 结果 → stale；再点旧图只增加拒绝记录。
3. unknown 同样使图过期；明确失败不会使可用图过期。重新截图后恢复。
4. 录制完整经历预检／采集／合成／校验；在预检等待时重复点击及调整帧数都无效。输出 `.mov`、实测标注与缺帧提示。「再录一段」不自动开始。
5. 配额拒绝先于采集；缩短只更新帧数；配额不可读明确区别于预检成功。
6. 切去 Trace 再返回保留 Device 状态；切换新评审场景不接收上个场景的迟到结果。
7. 用中英文、浅／深色以及内容区 880 pt 两侧的宽度检查控制可达性、滚动与留白。

本轮原生 `AppShellUITests/testDeviceWorkspaceNameAndEmptyStateInBothLanguages` 与 `testDeviceRecordingLocksControlsWhileCheckingStorage` 通过。后者用延迟配额响应复现并修复预检期间按钮仍可用的问题，并验证拒绝后恢复、缩短帧数不自动开录。两项都使用 App fixture，只证明名称、空态、控件状态与本地呈现，**不是本轮真机操作验收**。设计截图及复现入口见 [`references/v1.5/README.md`](references/v1.5/README.md)。

## 7. 真机与部署边界

2026-08-27 的真实设备为 OpenHarmony 3.2 / OpenHarmony-7.0.0.38，720×1280，HDC 3.2.0f，精确 binding r4。CLI 已执行真实截图、输入与 40 帧采集；App 使用同一已安装 Runtime，未注入设备／录屏 fixture。

已安装 Runtime 的 XPC 白名单漏接 `capture.screen-sequence@1`：App 录屏在提交前被拒绝，没有录屏 Job，也没有 `.mov`，因此 **App 录屏端到端验收仍为 `BLOCKED_BY_PRODUCT_DEFECT`**。本轮代码已补齐准确 client/operation/version 的入口，保留一次性 Job gate 和 Runtime 准入；修复需经维护者 review 合入 main、更新受保护 Runtime 后再验。HTML ready 仅供评审，不是该缺陷已在真机修复的证明。

另外修复了回执对未选择截图编码、无文件输出手势的错误制品要求；没有修改已安装 Runtime 的历史回执、真实制品或 Core 验收规则。运行记录与原始证据位置见 [`real-device-validation.md`](references/v1.5/real-device-validation.md)。
